## 23 August 2026 - Event-source the case store, with no stored status column
**The problem (plain English):** The defect this project exists to fix is that a government spreadsheet had four columns of numbers that did not add up, and nobody could say why. A system that stores "current status" as a field can always drift away from what actually happened to the application.
**What we decided (plain English):** Never store where an application is. Store what happened to it, one immutable record at a time, and work out where it is from that.
**How it works technically:** `src/core/caseStore.ts` holds an append-only array of `CaseEvent`s. There is no update and no delete. `src/core/projections.ts` derives current stage, days in stage, breach status, the stepper model and the audit trail from that log. `Application` deliberately has no `currentStage` field. A correction is a compensating event, never an edit.
**Why this and not something else:** A mutable status column is faster to write and is exactly the shape of the original bug. Event sourcing is also what makes the reconciliation engine possible at all — you cannot detect a contradictory history if you have already overwritten it.
**Files touched:** `src/core/types.ts`, `src/core/caseStore.ts`, `src/core/projections.ts`.

## 23 August 2026 - Make a reason-free rejection structurally impossible
**The problem (plain English):** A review left on the government's own UDID app in April 2026 says the app gives "absolutely no notification regarding the rejections", and that hospital staff offer no explanation either. A policy saying "always give a reason" does not fix that, because policies are not enforced by software.
**What we decided (plain English):** An officer cannot return or reject a case without picking a structured reason from a fixed list. Not "should not" — cannot.
**How it works technically:** `buildTransitionEvent()` in `src/core/transitions.ts` validates every write and throws `TransitionError` with code `REASON_CODE_REQUIRED` if a move to `RETURNED_FOR_DOCUMENT` or `REJECTED` carries no code, or `UNKNOWN_REASON_CODE` if the code is not in the catalogue. Every write into the store goes through it. The officer console additionally disables the buttons until a code is chosen, and carries a "Try returning it with no reason" control that bypasses the UI and prints the refusal, so the enforcement is visible rather than claimed.
**Why this and not something else:** Validating in the UI alone would leave the rule one refactor away from disappearing. Putting it in the store means every future screen inherits it.
**Files touched:** `src/core/transitions.ts`, `src/core/reasonCodes.ts`, `src/screens/OfficerScreen.tsx`, `src/tests/stateMachine.test.ts`.

## 23 August 2026 - Preserve the queue place by default, and lose it only by name
**The problem (plain English):** If a case is sent back because a photocopy was blurry, and the applicant then goes to the back of a queue that averages 253 days, the punishment for an administrative slip is another eight months. That is a good way to make someone give up entirely.
**What we decided (plain English):** Keep the applicant's place in the queue whenever the fault was something the office could have caught earlier. Only a genuine applicant-side failure moves them to the back, and the reason code has to say so explicitly.
**How it works technically:** Each reason code carries `preservesQueuePosition`. `queueAnchorAt()` in `src/core/queue.ts` walks the event log and keeps the original submission timestamp as the sort key, moving it to the resubmission only when a non-preserving code was recorded. Of the seven codes, only `BOARD_NO_SHOW` does not preserve. The track and fix screens state which applies and why, in a sentence.
**Why this and not something else:** Defaulting the other way would have been easier to implement and would have quietly reproduced the behaviour we are objecting to.
**Files touched:** `src/core/queue.ts`, `src/core/reasonCodes.ts`, `src/screens/TrackScreen.tsx`, `src/screens/FixScreen.tsx`.

## 23 August 2026 - Pin the clock instead of reading the machine's
**The problem (plain English):** Every number in the demo — days waiting, breaches, the 211-day case in the hero — depends on what "today" is. Read the real clock and the walkthrough drifts a little further from its script every day, and the tests become unreliable.
**What we decided (plain English):** Fix "now" at 23 August 2026, 09:00 IST, and generate the whole dataset backwards from it.
**How it works technically:** `DEMO_NOW` in `src/core/clock.ts` is a single constant; `daysBetween()` and the generator both default to it. **Files touched:** `src/core/clock.ts`, `src/data/generator.ts`.

## 23 August 2026 - Write a data generator, and plant defects in it on purpose
**The problem (plain English):** A district dashboard is meaningless over a handful of records, and a fixture file large enough to be meaningful is unreadable. Separately, the reserved reconciliation engine needs broken cases to find, and they have to be reproducible.
**What we decided (plain English):** Generate the dataset from a fixed seed, and deliberately break thirteen things in it, each one described in writing.
**How it works technically:** `src/data/generator.ts` uses a `mulberry32` seeded PRNG to build 1,416 applications and 5,411 events across six Madhya Pradesh districts, with a dwell-time distribution that puts about half of all open cases past their proposed target — the published figures describe a 253-day average, so a wall of green would misrepresent them. `buildPlantedDefects()` then writes broken records as raw event objects, bypassing the state machine the way a legacy import or a direct database edit would, and returns a manifest naming each one. The oversight screen lists that manifest, clearly labelled as the generator describing itself and not a reconciliation result.
**Why this and not something else:** Hand-written fixtures could not have produced a believable district dashboard, and defects introduced at random would not have been reproducible enough to write a test suite against.
**Files touched:** `src/data/generator.ts`, `src/bootstrap.ts`, `src/screens/AdminScreen.tsx`.

## 23 August 2026 - Write the router by hand rather than add a dependency
**The problem (plain English):** The app needed seven screens with shareable addresses. The obvious move is to install a routing library.
**What we decided (plain English):** Write a forty-line hash router instead.
**How it works technically:** `src/lib/router.tsx` exports `useRoute()`, `navigate()` and a `Link` that renders a real anchor with a real href, so middle-click, copy-link and the screen-reader link rotor all behave normally. Hash routing also means the built site works from any static host with no server rewrite rules.
**Why this and not something else:** A router library would have added more to the bundle than the entire rest of the application. This is a service for people on cheap phones and slow connections, where a kilobyte is a real cost. The trade-off is that we own the edge cases — one of which bit immediately, see below.
**Files touched:** `src/lib/router.tsx`, `src/App.tsx`.

## 23 August 2026 - Three bugs the tests caught, and what they were
**The problem (plain English):** Three things looked right and were not. All three would have been visible in a demo.
**What we decided (plain English):** Fix each at the cause rather than working around it in the test.
**How it works technically:** (1) The skip link's `href="#main"` set the URL hash, which the hash router read as a route change to `/main` and rendered the not-found screen — so the first keyboard action on every page broke the page. It now prevents the default and moves focus by hand, while staying a real anchor. (2) The route-change focus effect used a first-render boolean, and StrictMode's double-invoked effects let the second pass steal focus onto `<main>` before the user had pressed anything, skipping past the skip link. It now compares the previous path. (3) After a successful resubmission the fix screen fell through to its own "nothing to fix" guard, because the case was no longer returned — so the confirmation never appeared. It now remembers the outcome rather than deriving it from a case that has moved on.
**Why this and not something else:** Each of these is the kind of thing that only shows up when you actually drive the app, which is why the golden path is a test rather than a checklist.
**Files touched:** `src/ui/Layout.tsx`, `src/App.tsx`, `src/screens/FixScreen.tsx`.

## 23 August 2026 - Give the focus ring a dark edge, and make scrollable tables focusable
**The problem (plain English):** Two accessibility failures found by measurement rather than by eye. The yellow focus ring is only 1.64:1 against white, well under the 3:1 a focus indicator needs. And a table that scrolls sideways on a phone was unreachable by keyboard — you could see there was more to the right and had no way to get to it.
**What we decided (plain English):** Paint the yellow ring over a dark one, and make every scrollable table a named, focusable region.
**How it works technically:** `:focus-visible` sets a 3px `--focus` outline with a 2px offset over `box-shadow: 0 0 0 7px var(--ink)`, giving a dark edge on both sides of the yellow; `--focus` against `--ink` is 9.80:1. `src/ui/TableScroll.tsx` wraps every wide table in a `role="region"` with `tabIndex={0}` and an `aria-label`, which is what axe's `scrollable-region-focusable` rule asks for. All twenty-four accessibility checks now pass on both mobile and desktop viewports.
**Why this and not something else:** Suppressing the axe rule would have left a real barrier in a service specifically for people with disabilities. Computed ratios for every token pair are recorded in STYLE.md, including the two that sit below 3:1 on purpose and why that is defensible.
**Files touched:** `src/styles/base.css`, `src/ui/TableScroll.tsx`, `STYLE.md`, `e2e/accessibility.spec.ts`.

## 23 August 2026 - Publish the medical board calendar, and give people a date
**The problem (plain English):** A reviewer pushed back on the whole project: a tracking screen is about a month of work for a government vendor, so what is the big deal? Half of that is right. The tracking screen is not the big deal — the rule underneath it is, and that rule is the piece reserved for Codex. But the other half landed. We were showing the delay and not removing it. The research had already identified the medical board as the actual bottleneck, and we had cut it as out of scope.
**What we decided (plain English):** Publish every district board's calendar, capacity and queue, and turn a queue position into an expected date. Treat the doctors' panel the way an airline treats seats.
**How it works technically:** `src/core/boardSchedule.ts` holds sitting days and slots per sitting for each of the six districts, and derives weekly capacity, the next sittings, weeks of backlog, and a forecast date by walking forward through sittings until the queue position is covered. `src/lib/useBoard.ts` derives each district's queue from the same event log everything else reads — sorted by the queue anchor, so a place protected after an administrative return is protected here too, at the one stage where losing it costs the most. `#/board` publishes the lot; the track page shows the applicant their own position, sitting days, venue and expected date. **Why this and not something else:** The minister's own answer in Parliament is that board scheduling depends on "the availability of doctors" — the scarcest resource in the system is unplanned, and that is what produces a 253-day average. Every input an expected date needs already exists in a district hospital: a room, a panel, and a number of people it can see in a day. Publishing them is not hard; it is just never done, because a published date is a commitment. The alternative we rejected was booking real slots, which would have meant modelling holidays, absent specialists and re-planning after a missed sitting — a lot of machinery for a demo, and it would have turned a forecast we can honestly label into a promise we cannot keep.
**One thing we deliberately did not do:** dress the forecast up as a booking. Every screen it appears on says it is arithmetic on a published cadence, not a reservation. A date that turns out wrong can be challenged; silence cannot. Each district card also holds the published cadence against what finished cases actually took at that board, because publishing a calendar nobody checks is decoration.

**The problem (plain English):** The interface was called bad, and measurement agreed. ## 24 August 2026 - Put the accessibility toolkit in the page chrome
**The problem (plain English):** Every major Indian government portal carries display controls — contrast, text size, spacing — as a persistent toolkit in the page chrome. india.gov.in goes furthest, with text spacing, line height, hide images and a big cursor. This is a service for persons with disabilities and it had none of them.
**What we decided (plain English):** Add a toolkit bar above the header: text bigger, text smaller, reset, and high contrast, on every page, in both languages.
**How it works technically:** `src/core/displaySettings.ts` holds the state and writes it onto the document root; text size scales the root font size across three steps (100% / 112.5% / 125%) so every `rem` in the token system follows it and no second set of values is needed. High contrast sets `data-contrast="high"`, which swaps the tokens for maximum-separation equivalents, thickens borders — a hairline vanishes at high contrast — and underlines every link. Both persist to localStorage and are applied before the first paint. The contrast control is a real `aria-pressed` toggle, so its state is announced rather than only shown, and the size buttons disable at the ends rather than silently doing nothing.
**Why this and not something else:** Browser zoom already exists, and is not a substitute: plenty of people do not know it is there, are on a borrowed phone, or are being helped through the form by someone else. A control you can see is one you can use. Building it also cost nothing structurally, because the design system was already tokens all the way down.

## 24 August 2026 - Give the clock teeth: the statutory limit and escalation
**The problem (plain English):** The honest criticism of the whole project was that it shows you the delay and does nothing about it. A case 211 days old displayed a red number and offered the applicant no action at all — which is a more articulate version of the same helplessness. Worse, we had been framing every deadline as "our proposal", when research found that a legal deadline already exists.
**What we decided (plain English):** Count the deadline the law already gives, show it, and let the citizen escalate when it passes.
**How it works technically:** `src/core/escalation.ts` holds the statutory clock and the ladder. The Rights of Persons with Disabilities Rules, 2017, rule 18, as amended by the RPwD (Amendment) Rules, 2024 (in force 18 October 2024), give the certifying authority three months to issue a certificate and card — so `RPWD_CERTIFICATE_LIMIT_DAYS` is 90, counted from the application date. A new `ESCALATED` event type records a raise without moving the case, because escalation adds accountability and does not conjure a doctor. The track page shows the limit second, after the holder; `#/escalate/:id` raises it; the officer queue flags escalated cases, filters to them and sorts them above equally-late cases nobody has raised; the oversight dashboard counts them. The generator seeds escalations onto a fifth of the cases that ran well past the limit, so the staff screens show real pressure rather than a clean slate.
**Where the line is between law and proposal:** The RPwD three-month limit is verified and cited on screen. The escalation ladder — First Appeal Officer, then Second Appellate Authority, with 30-day and 60-day windows — is modelled on the Madhya Pradesh Lok Sewaon Ke Pradan Ki Guarantee Adhiniyam, 2010, sections 3, 6 and 7, and is labelled as modelled rather than claimed. What could **not** be verified is whether a disability certificate is a notified service under that Act, and against what time limit — the state's service list would not load. So the interface never tells an applicant that the Act's Rs 250-per-day penalty is owed to them. It records the delay and sends it up, and says on the page that the penalty question is unverified. Telling a disabled person they are owed money they may not be owed would be a worse failure than saying nothing.
**Why this and not something else:** An automatic escalation with no human on the other end would have been theatre. Recording the raise, naming the authority, dating it, and making it visible to the officer and the oversight dashboard is the part a software system can honestly do — and it is exactly what the current service does not.

## 25 August 2026 - Refuse to resolve contradictory event history
**The problem (plain English):** A convenience projection can sort stage events and pick the last one. If two different stage events share the newest timestamp, that produces a plausible-looking answer while silently choosing between contradictory facts.
**What we decided (plain English):** The reconciliation engine names that case as `CONTRADICTORY_HISTORY` and excludes it from stage counts. It does not guess which desk owns the application.
**How it works technically:** `reconcile()` reads the raw event log, groups and orders events deterministically, compares all newest stage moves at the latest timestamp, and creates both an orphan and an anomaly when their destinations differ. Counts always include every modelled stage; `gap` is derived only from those counts.
**Why this and not something else:** A balanced total created by choosing a convenient state is the exact silent-loss failure this service exists to prevent. Uncertainty must be visible and actionable, even when it makes the dashboard look worse.
**Files touched:** `src/core/reconciliation.ts`, `src/screens/AdminScreen.tsx`.
